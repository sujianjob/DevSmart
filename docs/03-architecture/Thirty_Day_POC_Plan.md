# 30 天 POC 详细目标

> 状态：规划更新版
> 适用范围：DevSmart 第一阶段概念验证
> 迁移策略：无迁移，直接替换旧版“大而全”POC 规划

---

## 1. 目标定义

30 天目标不是交付完整商业化平台，而是交付一个可演示、可内测、可验证核心价值的 **AI 研发流程指挥中心**。

最小闭环如下：

```text
需求输入 -> PRD 生成/澄清 -> 人工审批 -> 任务拆解 -> 上下文包生成 -> 流程状态展示 -> 审计事件记录
```

该闭环要验证一个核心假设：DevSmart 能否把一句模糊需求，转化为产品、技术负责人和研发都能使用的结构化任务输入。

---

## 2. 第 1 周：工程骨架与状态机

### 2.1 交付内容

- `backend/`：FastAPI 服务骨架。
- `frontend/`：React + Vite 控制台骨架。
- `prompts/`：提示词目录。
- `.ai-context/`：POC 运行上下文目录。
- 基础 API：
  - `POST /tasks`：创建需求任务。
  - `GET /tasks/{id}`：查询任务状态。
  - `GET /tasks/{id}/events`：读取流程事件。
  - `POST /tasks/{id}/approve`：人工审批。
  - `POST /tasks/{id}/reject`：驳回并补充意见。

### 2.2 状态机

```text
created
  -> prd_generating
  -> clarifying
  -> pending_approval
  -> task_splitting
  -> context_packaging
  -> completed
```

异常与人工分支：

```text
pending_approval -> rejected
任意状态 -> failed
```

### 2.3 验收标准

- 输入一条需求后，系统能创建任务 ID。
- 前端能展示任务状态变化。
- 后端能记录每一步事件。
- 审批和驳回接口可用。

---

## 3. 第 2 周：PM Agent 与 PRD 生成

### 3.1 交付内容

- PM Agent 初版。
- PRD 生成提示词。
- PRD JSON Schema。
- PRD Markdown 渲染。
- 澄清问题生成能力。
- PRD 一致性检查初版。

### 3.2 PRD 内容要求

PRD 至少包含：

- 背景说明。
- 用户角色。
- 用户故事。
- 功能范围。
- 非功能需求。
- 验收标准。
- 边界条件。
- 不做什么。
- 风险与待确认问题。

### 3.3 系统行为

- 需求足够清楚时，直接生成 PRD 初稿。
- 需求模糊时，生成 3-5 个澄清问题。
- 用户补充后，重新生成 PRD。
- PRD 生成后进入人工审批状态。

### 3.4 验收标准

- 输入“做一个团队任务管理功能”，能生成完整 PRD。
- PRD 中必须包含用户故事和验收标准。
- 模糊需求能触发澄清问题。
- 用户驳回后，PM Agent 能基于反馈重新生成。

---

## 4. 第 3 周：任务拆解与上下文包

### 4.1 交付内容

- Supervisor Agent 初版。
- Task Splitter 能力。
- Coder Coordinator 初版。
- `task_context.json` 生成能力。
- 任务列表页面。
- 单任务详情页面。

### 4.2 任务拆解结果

每个任务至少包含：

- 任务标题。
- 任务描述。
- 所属功能模块。
- 输入依赖。
- 输出产物。
- 验收标准。
- 推荐执行者类型。
- 优先级。
- 风险等级。
- 相关 PRD 片段。

### 4.3 上下文包结构

```json
{
  "task_id": "task_xxx",
  "prd_summary": "需求摘要",
  "acceptance_criteria": [],
  "technical_constraints": [],
  "suggested_files": [],
  "api_contracts": [],
  "test_scenarios": [],
  "open_questions": []
}
```

30 天版本不要求真实分析代码仓库。允许通过以下方式模拟上下文：

- 用户手动填写技术栈。
- 从 `/docs` 读取架构约束。
- 从 PRD 中提取接口、页面和数据对象。
- 生成“建议相关文件”，但必须标记为 AI 推测。

### 4.4 验收标准

- 一个 PRD 至少能拆出 3-8 个任务。
- 每个任务都有明确验收标准。
- 每个任务都有上下文包。
- 上下文包能被复制给 Cursor、Claude Code、Codex、Copilot 等外部工具使用。

## 5. 第 4 周：指挥中心、审计与演示闭环

### 5.1 交付内容

- Web 指挥中心。
- 需求输入框。
- PRD 预览与审批卡片。
- 任务拆解看板。
- 流程状态图。
- 事件时间线。
- 审计日志。
- Demo 数据集。
- 内测说明文档。

### 5.2 页面范围

第一阶段只做 4 个页面：

1. **任务创建页**：输入自然语言需求。
2. **PRD 审批页**：查看、批准、驳回或补充 PRD。
3. **任务拆解页**：查看任务列表和上下文包。
4. **流程回放页**：查看事件流、工具调用、输入输出摘要、审批记录和状态变更。

### 5.3 验收标准

- 能现场演示从需求输入到任务上下文包生成。
- 人工审批和驳回流程可用。
- 每个关键动作都有事件记录。
- Demo 不依赖真实 Jira、GitHub、CI/CD。
- 至少准备 5 个典型需求样例跑通。

---

## 6. 完成后系统能力

### 6.1 产品经理能力

产品经理可以输入自然语言需求，系统自动生成 PRD 初稿、用户故事、验收标准、边界条件、风险提示和待确认问题。

### 6.2 技术负责人能力

技术负责人可以审批 PRD、驳回补充、查看任务拆解结果、判断任务优先级和依赖，并把任务包分配给人类开发者或外部 Coding Agent。

### 6.3 研发工程师能力

研发工程师可以拿到任务说明、PRD 摘要、验收标准、技术约束、建议相关文件、测试场景和开放问题，减少需求澄清成本。

### 6.4 团队管理者能力

团队管理者可以看到需求处理状态、PRD 审批状态、任务拆解状态、流程耗时和关键阻塞点。

---

## 7. 明确不包含

30 天版本不包含：

- 完整 Jira/Linear 双向同步。
- CI/CD 自动触发。
- 代码自动提交。
- 生产级权限体系。
- 多租户计费。
- 完整知识图谱。
- Milvus / Neo4j / K8s 生产部署。
- 模型内部 Chain of Thought 展示。
- 企业版私有化部署。

## 8. 核心验证指标

| 指标 | 30 天目标 |
|:---|:---|
| PRD 生成成功率 | ≥ 80% |
| PRD 初稿可采纳率 | ≥ 50% |
| 任务拆解可采纳率 | ≥ 60% |
| 从需求到任务包耗时 | ≤ 10 分钟 |
| 内测用户愿意继续使用比例 | ≥ 60% |
